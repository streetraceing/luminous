# Luminous contributor rules

These rules apply to all work in this repository.

1. Update the relevant documentation whenever a change materially affects architecture, runtime behavior, settings, performance characteristics, development workflow, or user-facing functionality.
2. Preserve the visual style and overall structure of the root `README.md`. Only update its factual information when necessary; do not redesign, reformat, or reorganize it unless the user explicitly asks for that.
3. Never change the project version manually — not in `package.json`, not in the `?version=` strings of `manifest.json` — and never run, edit, invoke, create, or replace `vite/releaseScript.ts`, `npm run release`, `npm:patch`/`npm:minor`/`npm:major`, `npm version`, or equivalent release/version automation. The agent never applies version updates; it only proposes them in the reply.
4. Judge every change set for whether a release is warranted and recommend exactly one of `none`, `patch`, `minor`, or `major` on its own line in the reply. Base it on real user-facing impact rather than the commit type alone: `none` when the shipped theme is unaffected (metadata, docs, comments, formatting, internal cleanups — `chore: changed package description`, for example, needs no version), `patch` for backward-compatible fixes, `minor` for new user-facing functionality or settings, and `major` only when existing setups break (settings/profile compatibility, removed features, a required re-apply or reinstall).
5. After completing a set of changes, end the reply with a brief commit-style message on its own line, formatted as `<type>: <summary>` where `<type>` is one of `feat`, `fix`, `chore`, `docs`, `refactor`, `perf`, `test`, or `build` (for example: `fix: handle missing artwork without clearing the background`). The message is report-only for the operator to reuse as a git commit subject; never create git commits unless the user explicitly asks for that.
